# Durable Object 알람 기반 감시 전환 설계

- 작성일: 2026-10-09
- 상태: 승인됨 (구현 착수)
- 범위: 2단계 — 1분 Cron 감시를 Durable Object 알람 기반 10초 간격 감시로 전환

## 배경

현재 감시는 Cloudflare Cron(최소 1분)으로 매분 네이버 예약을 한 번 조회합니다. 빈자리가 생긴 뒤 감지까지 평균 약 32초, 최대 약 63초가 걸립니다. 인기 디자이너의 취소분은 다른 사람과 경쟁해야 하므로 이 지연을 줄이는 것이 목표입니다.

### 실측값 (2026-10-06 ~ 10-09)

| 항목 | 값 |
|---|---|
| 네이버 응답 시간 (한국 PC) | 0.15~0.35초 |
| 네이버 조회 시간 (Worker Cron) | 0.75~1.46초 |
| 응답 크기 (10월 말까지) | 135KB, gzip 3.9KB |
| 응답 캐시 | `cache-control: no-store` |
| Cron 예정 시각 대비 시작 지연 | 0.2~1.8초 |
| Cron 실행 1회 CPU 시간 | 1~2ms |

### 검토한 대안

| 방식 | 판단 |
|---|---|
| A. Durable Object 알람 자가 예약 | 채택. 무료 플랜, 정확한 간격, 즉시 일관성 저장소 |
| B. Durable Object 안 `setTimeout` 루프 | 기각. hibernation이 막혀 duration 10,800 GB-s/일 전부 과금 |
| C. 유료 플랜 + Cron 안 반복 | 차선. 월 $5, 분 경계마다 KV 전파 지연으로 누락 가능 |

간격은 10초를 하한으로 정했습니다. 10초에서 5초로 줄이면 평균 감지 지연이 2.5초만 줄어드는데, 호출량은 두 배가 되고 네이버의 차단 기준은 알 수 없기 때문입니다.

## 목표

- 주간 평균 감지 지연을 약 6초로 줄입니다.
- 무료 플랜 안에서 동작합니다.
- 감시가 멈추면 Slack으로 알립니다.
- 전환 과정에서 이미 알린 빈자리를 다시 알리지 않고, 새 빈자리를 놓치지 않습니다.

## 범위 밖

- 빈자리 수명(열린 뒤 마감까지 걸린 시간) 기록
- `watch.py`와 GitHub Actions 워크플로
- Worker 전체가 멈추는 장애의 감지 (외부 생존 신호 서비스)

## 1. 구조

```
Cloudflare Worker (naver-slot-watch)
 ├─ Watcher (Durable Object, 이름 "main" 하나, 위치 apac-ne)
 │   ├─ alarm(): 한 회차 실행 (core.runCycle)
 │   ├─ ensure(): 알람이 없으면 다시 걸고 상태를 돌려줌 (RPC)
 │   └─ 저장소: 디자이너별 빈자리 목록, meta
 ├─ Cron 1분 (감시자)
 │   ├─ Watcher.ensure() 호출
 │   └─ 멈춤 판정 시 Slack "감시 멈춤" 알림, 복귀 시 "감시 재개" 알림
 └─ HTTP /go/<itemId> (중계 페이지, 변경 없음)
```

| 파일 | 역할 |
|---|---|
| `worker/src/index.js` | 진입점: 중계 페이지, Cron 감시자, Watcher 내보내기, stub 생성 함수 |
| `worker/src/watcher.js` | Watcher 클래스: 저장소 인터페이스를 `core.runCycle`에 연결 |
| `worker/src/core.js` | 순수 로직: 네이버 조회, 빈자리 비교, 메시지, 실패 상태 전이, 간격 계산, 감시자 판정, 한 회차 흐름 |
| `worker/test/core.test.mjs` | `node --test` 단위 테스트 (새 의존성 없음) |

- `core.js`는 Cloudflare 전용 모듈을 가져오지 않습니다. 시계와 무작위 값은 인자로 주입합니다.
- stub은 `getWatcher(env)` 함수 하나로만 만듭니다. `locationHint`는 객체가 처음 만들어질 때만 적용되므로, 힌트 없는 경로가 있으면 객체 위치가 다른 곳에 고정될 수 있습니다.
- Cron에서는 조회 로직을 완전히 뺍니다. 두 감시자가 같은 빈자리를 따로 알리지 않게 하기 위해서입니다.
- `TEST_MESSAGE`는 Cron에서 매분 발송하는 동작을 유지합니다. `TEST_DESIGNERS`는 Watcher가 함께 조회합니다.

### 저장소

| 위치 | 키 | 값 | 쓰는 때 |
|---|---|---|---|
| Watcher | `slots:<itemId>` | 빈자리 목록 | 목록이 바뀔 때 |
| Watcher | `meta` | `{ lastCompletedAt, delay, failures, health }` | 회차가 끝날 때 |
| KV | `watchdog` | `{ failSince, alerted }` | 감시자 상태가 바뀔 때 |
| KV | `<itemId>`, `health` | 1단계의 상태 | 쓰지 않음. 전환 시 기준값으로 1회 읽고, 검증 후 삭제 |

## 2. 한 회차의 데이터 흐름 (`core.runCycle`)

```
1. 정지 스위치가 켜졌거나 WATCH_END 가 지났으면 알람을 지우고 종료
2. 다음 알람 예약: now + 기본 간격
3. 감시 대상 = DESIGNERS + TEST_DESIGNERS
4. 디자이너별:
   a. 네이버 조회 (지난 칸 제외)
   b. 직전 목록: Watcher 저장소 → 없으면 KV의 기존 키 (전환용)
   c. 새 빈자리가 있으면 Slack 발송 → 그다음 목록 저장 (바뀐 경우만)
5. 감시 대상에서 빠진 디자이너의 slots 키 삭제
6. 실패 상태 갱신 (3분 이상 실패 시 장애 알림 1회, 복구 시 복구 알림)
7. 실패가 있으면 다음 알람을 늘어난 간격으로 다시 예약
8. meta 저장
```

- **다음 알람을 먼저 예약합니다.** 알람 재시도는 가장 최근에 건 알람에만 적용되므로, 이후 단계에서 예외가 나도 루프가 이어집니다.
- **알림 다음에 저장합니다.** 중간에 끊기면 같은 알림이 한 번 더 갈 수 있지만, 순서를 바꾸면 알림이 누락될 수 있습니다. 이 시스템에서는 중복이 누락보다 낫습니다.
- **KV 기준값은 Watcher 저장소에 키가 없을 때만 읽습니다.** KV에도 없는 디자이너는 지금처럼 첫 회차에 현재 빈자리를 모두 알립니다. README의 `TEST_DESIGNERS` 검증 절차가 그대로 유지됩니다.
- **`lastCompletedAt`은 8단계까지 와야 갱신됩니다.** 매번 중간에 예외로 끝나는 경우도 감시자가 잡을 수 있습니다.
- **저장소 쓰기량** — 회차당 알람 1행과 meta 1행이므로 하루 약 13,400행입니다. 무료 한도는 하루 10만 행입니다.

### 간격 계산 (`core.nextDelay`)

| 시간대 (한국 시간) | 기본 간격 |
|---|---|
| 8~24시 | 10초 ± 2초 무작위 |
| 0~8시 | 30초 ± 2초 무작위 |

연속 실패 횟수가 n이면 `기본 간격 × 2ⁿ` 으로 늘리고 5분에서 멈춥니다. 한 번 성공하면 기본 간격으로 돌아갑니다.

## 3. 오류 처리와 운영

### 실패 판정

HTTP 오류, GraphQL 오류, JSON이 아닌 응답, 응답 구조 변경을 실패로 셉니다(1단계와 같음). 장애 알림은 실패가 3분 이상 이어진 뒤 첫 회차에 나가므로, 간격이 늘어난 상태에서는 3~5분 사이에 갑니다.

### 감시자 판정 (Cron 1분)

| 상황 | 판정 |
|---|---|
| `ensure()` 호출 실패 | 실패가 3분 이상 이어지면 멈춤 |
| `now - lastCompletedAt > max(3분, delay + 1분)` | 멈춤 |
| 정지 스위치 켜짐 또는 감시 기간 종료 | 판정하지 않음 |

- 멈춤 판정이 나면 한 번 알리고, 정상으로 돌아오면 재개를 알립니다.
- 호출 실패에 3분 유예를 두는 이유는 배포할 때 Durable Object가 재시작되면서 RPC가 잠깐 실패하기 때문입니다.
- 판정 기준에 `delay`를 넣는 이유는 간격이 5분까지 늘어난 정상 상태를 멈춤으로 오판하지 않기 위해서입니다.

### 정지 스위치

- `WATCHER_PAUSED` 변수를 설정해 배포하면 `alarm()`과 `ensure()`가 알람을 다시 걸지 않습니다.
- `WATCH_END`가 지나도 같은 경로로 멈춥니다.
- 변수를 빼고 배포하면 1분 안에 감시자가 알람을 다시 겁니다.
- Durable Object를 도입한 뒤에는 `wrangler rollback`으로 이전 버전에 돌아갈 수 없습니다. 문제가 생기면 스위치로 멈춘 뒤 수정 코드를 배포합니다.

### 받아들이는 한계

감시자와 Watcher가 같은 Worker에 있으므로, 계정 정지·Worker 삭제·하루 요청 한도 초과처럼 Worker 전체가 멈추는 장애는 알 수 없습니다. 1단계와 같은 한계이며 README에 적어 둡니다.

### 배포 절차

1. `wrangler deploy --dry-run`으로 Durable Object 설정을 검증합니다. `exports` 블록(`"storage": "sqlite"`)을 우선 시도하고, 지원되지 않으면 `migrations`(`new_sqlite_classes`)를 씁니다.
2. 배포합니다. 첫 Cron이 `ensure()`를 부르면서 객체가 만들어지고 알람이 시작됩니다.
3. `wrangler tail`로 주기와 `naver=` 값을 확인합니다.
4. 한 번 더 재배포해서 알람이 이어지는지 확인합니다.
5. 정상 동작을 확인한 뒤 KV의 `health`·`4347340` 키를 지우고 README를 갱신합니다.

배포 직후 몇 분 동안은 이전 버전의 Cron이 함께 돌 수 있습니다. 그 사이에 새 빈자리가 생기면 알림이 두 번 갈 수 있지만 누락은 생기지 않습니다.

### 무료 플랜 사용량 예상

| 항목 | 한도 | 예상 |
|---|---|---|
| Durable Object 요청 | 하루 10만 | 약 8,200 (알람 약 6,700 + `ensure()` 1,440) |
| Durable Object duration | 하루 13,000 GB-s | 최악 10,800 (실제는 hibernation으로 더 적음) |
| SQLite 행 쓰기 | 하루 10만 | 약 13,400 |
| Worker 요청 | 하루 10만 | 약 1,440 (Cron) |
| KV 읽기·쓰기 | 하루 10만·1,000 | 약 1,440·상태 전이 때만 |

## 4. 테스트

### 단위 테스트 (`node --test worker/test/*.test.mjs`)

| 대상 | 확인할 것 |
|---|---|
| `fetchFreeSlots` | 빈자리 판정 네 조건, 지난 칸 제외, 실패 네 종류 |
| 실패 상태 전이 | 3분 미만 무알림, 3분째 1회 알림, 재알림 없음, 복구 알림, 짧은 실패 후 무알림 |
| `nextDelay` | 07:59 → 30초, 08:00 → 10초, 무작위 폭 ±2초, 2ⁿ 증가, 5분 상한, 성공 시 초기화 |
| `runCycle` | 알람을 먼저 예약, KV 기준값 1회 이전, 빠진 디자이너 삭제, 중간 예외 시 `lastCompletedAt` 미갱신, 정지·기간 종료 시 알람 미예약 |
| 감시자 판정 | `delay` 반영 멈춤 기준, 호출 실패 3분 유예, 재개 알림 |

### 로컬 통합 확인 (`wrangler dev --test-scheduled`)

- `/__scheduled` 호출로 Cron을 흉내 내고, 알람이 약 10초 간격으로 1분 동안 이어지는지 봅니다.
- Slack 주소는 `.dev.vars`에 가짜 수신 서버를 넣어 실제 채널로 보내지 않습니다.

### 운영 확인

| 항목 | 완료 기준 |
|---|---|
| 주기 | 주간 로그 간격 8~12초 |
| 위치 효과 | `naver=` 중앙값이 약 1.2초보다 작음 (줄지 않으면 보고만 함) |
| 재배포 | 재배포 뒤 1분 안에 로그 재개 |
| 알림 경로 | `TEST_DESIGNERS` 추가 시 알림 1건, 다음 회차 0건, 제거 후 상태 자동 삭제 |
| 전환 | 현지 디자이너의 기존 빈자리 재알림 없음 |

운영 환경의 감시 멈춤 알림은 일부러 장애를 내야 하므로 단위 테스트로만 확인합니다.
